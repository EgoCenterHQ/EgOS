Part I
User guide

Welcome

Thank you for choosing EgOS, the system that turns a small home computer into a personal media centre: your photos, films, music and series, always at hand on every device in your home network, with no subscriptions and no third-party cloud.

This booklet takes you from installation to everyday use. Part I is for the people who use the box; Part II is for whoever administers it; Part III describes, script by script and function by function, how the system is built.

What EgOS does

Jellyfin watch films and series, listen to music from TV, phone, browser http://egocenter.local:8096
Immich backup and gallery for your phone's photos http://egocenter.local:2283

Contents and requirements

Edition For Installation medium
egos-4.3.0-amd64.iso x86-64 PC, mini PC, virtual machine USB stick (automatic installation)
egos-4.3.0-arm64.img Raspberry Pi 5 with NVMe SSD image written directly to the NVMe

You also need:

  • an Internet connection over an Ethernet cable (needed at the second boot to download the services);
  • a phone or a PC for the initial setup;
  • optional: one or more external USB disks for more space.

Warnings

Warning — Installing on a PC completely erases the target disk without asking for confirmation. If the computer has several disks, the installer asks which one to use: choose carefully.

Warning — Adding a disk to the pool erases everything on it. EgOS always asks, and wants you to type the disk's name to confirm.

Note — EgOS does not use RAID: if a data disk fails you lose the files that were on it, not those on the other disks. Keep a copy of important photos somewhere else.

Installation

On a PC (amd64)

  1. Write egos-4.3.0-amd64.iso to a USB stick (with dd, balenaEtcher, Rufus in DD mode, etc.).
  2. Connect the PC to the network with the Ethernet cable.
  3. Boot the PC from the stick (BIOS or UEFI, either works).
  4. The menu opens on Start installer and starts by itself after 5 seconds.
  5. The installation is fully automatic (about 5 minutes): Italian language, Italian keyboard, Europe/Rome time zone, machine name egocenter.
  6. When it is done the PC powers off. Remove the stick.

On a Raspberry Pi 5 (arm64)

  1. Connect the NVMe SSD to your PC with a USB adapter.
  2. Write egos-4.3.0-arm64.img to the NVMe with Raspberry Pi Imager → Use custom (or with dd from Linux).
  3. Fit the NVMe to the Pi 5. In the EEPROM, the boot order (BOOT_ORDER) must include the value 6 (NVMe): check it with rpi-eeprom-config.
  4. Connect the Ethernet cable and the power supply.

At the first boot the system grows its partition by itself to fill the whole NVMe.

Tip — With a monitor connected, the login screen shows the box's IP address and the useful addresses. Handy when the .local name does not work.

First boot: guided setup

At the first boot EgOS serves a small setup page. You can reach it in two ways.

Over Wi-Fi (if the box has Wi-Fi)

  1. On your phone, look for the Wi-Fi network SetupBox and connect.
  2. The network password is setup1234.
  3. The phone opens the "Sign in to network" page by itself; if it does not, open any http:// address in the browser.

Over the cable

From a PC on the same network open http://setupbox.local, or http://<box IP> (shown on the monitor connected to the box, or in your router's page).

Fill in the form

Field Used for
Email Immich administrator account
Username user for the system, Jellyfin, the shared folder and Cockpit
Password one password for all the services above

Press Complete Setup. "Setup Complete" appears: the box turns off the SetupBox network and reboots.

Warning — During setup the page is not protected: whoever fills it in first becomes the administrator. Do the first boot in a trusted environment and complete it straight away.

Second boot: automatic preparation

After the reboot the box, now reachable as egocenter.local, works on its own:

  1. it waits until the clock is synchronised and the Internet answers;
  2. it creates the folders for films, music, series, ROMs, downloads and photos;
  3. it prepares the shared folder with your username and password;
  4. it downloads and starts Immich and Jellyfin (a few GB: on a slow line this can take a long time);
  5. it creates your administrator account in Immich and Jellyfin;
  6. it starts the home page http://egocenter.local:8000, with a card for every service.

If something goes wrong (for example no Internet), the preparation retries at the next boot.

Watching and listening

Phone photos

Install the Immich app, enter http://egocenter.local:2283 as the server, sign in with the email and password from the setup and turn on automatic backup.

The administration console (Cockpit)

Open https://egocenter.local:9090. The browser reports an untrusted certificate (it is self-signed): accept the risk to continue. Sign in with your username and password. For disk operations click Limited access at the top right and enter your password again.

The Storage pool page is described in the next chapter. The Overview page shows a red banner only when a pool disk is missing.

The home page

Open http://egocenter.local:8000: one card for every service of the box, with a link to it. The page follows Docker by itself: a container that publishes a web page gets a card within 15 seconds (the optional services too, once enabled), a stopped one turns grey, one whose health check fails gets a yellow border. Cockpit always has its card. Databases and other non-web ports never appear.

Disks: the storage pool

EgOS gathers all the space into one big folder, the pool (/srv/egos/pool). At first the pool lives on the system disk; every disk you add joins the pool without moving anything and without stopping the services. Films, photos and the shared folder always see the same paths.

Situation Where new files go
No external disk system disk
One or more disks the disk with the most free space
A disk unplugged the other disks; that disk's files are not visible until it is back

Each disk needs at least 20 GB free to receive new files. Once there are data disks, the system disk no longer receives new files: if every data disk drops below 20 GB free, writes fail with a "read-only file system" error. This is intended: the system disk never fills up.

Adding a disk

From Cockpit: Storage pool → Disks that can be added → Add to pool → type the disk's name (e.g. /dev/sda) → Erase and add.

From a terminal: storage-add, choose the disk's number, type its name to confirm.

EgOS partitions and formats the disk, then runs an integrity test: it writes 128 MB of random data, reads it back and compares it, checks for kernel errors and measures the speed. A "fake" disk (counterfeit capacity) or a faulty one is rejected and does not join the pool.

Emptying the system disk

After you add a disk, the files already there stay on the system disk (visible and working). To move them: Empty system disk in Cockpit, or storage-drain. The paths do not change and the services keep working during the move. Files changed in the last 10 minutes are left for the next run. You can close the page: the operation carries on on the server.

Removing a disk

  1. With the disk still connected: Remove on its row (or storage-remove).
  2. Type the branch name (e.g. data1) to confirm. The disk is not formatted.
  3. Wait for the message YOU CAN NOW SAFELY UNPLUG THE DISK, then unplug it.

If it was the last disk, new files go back to the system disk.

If a disk gets disconnected

At boot EgOS waits 60 seconds for the disks, then starts anyway in degraded mode:

  • the missing disk's files are not visible;
  • Jellyfin stays off on purpose: otherwise its library scan would delete the missing titles together with their metadata and watch history;
  • Immich and the shared folder keep working;
  • a red banner appears in Cockpit (Overview and Storage pool) and at SSH login.

Plug the disk back in: it is remounted automatically within seconds and Jellyfin restarts. Alternatively press Retry missing disks (storage-reattach). If the disk is gone for good, press Remove on its row.

Architecture

EgOS is produced by two self-contained scripts that need no external files:

Script Output Build environment
EgOS4-arm64.sh ready-made image for the Pi 5 throwaway debian:trixie container + mmdebstrap + qemu-user (builder-arm64-raspPi/), or WSL2 Debian 13
EgOS4-amd64.sh ISO with automatic installer throwaway debian:trixie container + live-build (builder-amd64/)

The shared parts (services, webapp, stack, disk management, Cockpit page) are byte-for-byte identical in the two scripts.

1st BOOT
  egos-sshkeys ........ unique SSH keys per box
  egos-growroot ....... (Pi only) partition grown
  egos-pool ........... mergerfs pool on /srv/egos/local
  first-boot-setup
    └► setup-webapp.sh └► webapp.py :80 └► user └► reboot

2nd BOOT
  egos-pool └► docker, smbd
  docker-compose-startup
    └► deploy-compose.sh └► dirtree.sh └► wizardall2.sh
  egos-pool-guard ..... Jellyfin off if a disk is missing

ALWAYS
  udev "egos-data*" └► egos-reattach
    └► egos-storage _autoreattach

Building the images

amd64 (from any Linux with docker or podman): a throwaway container builds the ISO in its own filesystem and hands back only the ISO and the log.

builder-amd64/build-iso.sh                 # -> ./out/egos-<version>-amd64.iso
ENGINE=podman builder-amd64/build-iso.sh   # force podman

By hand, with podman:

mkdir -p ~/egos-amd64 && cd ~/egos-amd64        # the script only
sudo podman run -it --rm --privileged --network=host \
  -v "$PWD:/build:Z" -w /build debian:trixie bash
apt-get update && apt-get install -y live-build curl ca-certificates gnupg
bash EgOS4-amd64.sh 2>&1 | tee /build/build.log

To rebuild by hand, run lb clean first (not needed with builder-amd64/).

arm64 (from any Linux with docker or podman): the same throwaway-container approach. The container works in an ext4 loop file and registers the arm64 emulation (qemu, binfmt) only for the duration of the build.

builder-arm64-raspPi/build-img.sh          # -> ./out/egos-<version>-arm64.img

By hand (WSL2 Debian 13, folder on the WSL ext4, never /mnt/c):

sudo apt-get install -y mmdebstrap arch-test qemu-user qemu-user-binfmt \
    e2fsprogs dosfstools mtools fdisk curl ca-certificates
sudo bash EgOS4-arm64.sh 2>&1 | tee build.log
KEEP_ROOTFS=1 sudo -E bash EgOS4-arm64.sh       # quick rebuild

Both scripts stop with an error if a check fails: apt key fingerprints, critical packages missing or scheduled for removal, a second network manager, SSH keys in the image, missing files, unpinned versions.

Versions

Every change that ends up in the image bumps EGOS_VERSION (in both scripts). The installed system records the build data in /etc/egos-release. Docker images are pinned: Immich v3.2.2, Jellyfin 12.1, Valkey and Postgres by digest.

Usage

Each host command stops if the output folder already holds an ISO/image, so as not to overwrite it.

How it works (both)

  1. docker build --network=host (or podman build) creates the builder image from the folder's Dockerfile. It holds only the tools; it is rebuilt from the layer cache. .dockerignore keeps the build script out of the image.
  2. docker run --rm --privileged --network=host starts a throwaway container with: - the build script mounted read-only at /src; - the output folder mounted at /out (the only one shared with the host).
  3. Inside the container build-in-container.sh copies the script to /build, runs the build, copies only the image and the log to /out and gives them to the host user.
  4. When the build ends the container is deleted: no chroot, rootfs, cache or binary/ is left on the host (about 5 GB with the manual method), so no lb clean or rm -rf rootfs is needed between builds.

arm64 specifics (builder-arm64-raspPi/build-in-container.sh)

  • ext4 work folder: EgOS4-arm64.sh refuses any work folder that is not ext2/3/4 (it guards against WSL's DrvFs /mnt/c), and the container's own filesystem is overlayfs. The build therefore runs in a 30 GB sparse /work.ext4 file, attached to a free loop device and mounted on /build. /dev in a privileged container is a snapshot taken at start, so if the kernel hands out a new loop device the script creates its node with mknod. On exit: unmount, losetup -d, file deleted.
  • arm64 emulation: binfmt_misc belongs to the host kernel. If qemu-aarch64 is not registered, the script registers it from the container's /usr/lib/binfmt.d/qemu-aarch64.conf (flags OPF: the interpreter is opened at registration time, so it works inside mmdebstrap's chroot) and removes it on exit. If it was already registered on the host, it is left alone. Nothing is installed on the host.
  • The build itself is the unchanged EgOS4-arm64.sh: section 0 finds the emulation working (arch-test arm64).

Notes

  • Both need root + --privileged: live-build and mmdebstrap mount /proc and create devices in the chroot; the arm64 builder also needs loop devices and binfmt_misc. A rootless engine is not enough.
  • Every build downloads the packages again (~1 GB amd64, more for arm64).
  • Both build and run use --network=host: on some hosts the engine's bridge network cannot reach the internet (firewall/VPN dropping forwarded traffic, docker rules lost, DNS fallback blocked) and the build stops at the first apt-get update of the Dockerfile. With the host network the builder needs only what the host itself can reach.
  • Verified on 2026-10-29: amd64 with podman and Docker 29.9.2 (ISO installed in a VM up to the setup page); arm64 with Docker 29.9.2 (all section-14 checks, image contents inspected read-only; not boot-tested, there is no Pi 5 emulation).
  • The amd64 ISO also includes the udebs of the previous installer kernel (~33 MB more than the manual build with a cache): the installer uses only those of its own kernel.

Purpose

A launcher for the box: one card per service, with a link. It follows Docker by itself, so the optional stacks (egos-extras enable qbtt) and anything the user adds appear without editing a list.

How the cards are built

  1. Every request reads GET /containers/json?all=1 from the proxy (DOCKER_API, default http://127.0.0.1:23750).
  2. One card per container. Port: label egos.home.port, otherwise the first published TCP port (bound to all addresses) that answers HEAD / as HTTP, then as HTTPS. The probe result is cached for 10 minutes. Databases, BitTorrent, Redis… do not speak HTTP and never get a card.
  3. Name, description, icon, order: egos.home.* labels, otherwise defaults for known images (KNOWN: Immich, Jellyfin, qBittorrent, torrent-web, BentoPDF, Multi-scrobbler), otherwise the container name and image. Without icons/<id>.svg the card shows the initial on a colour derived from the name.
  4. State from Docker: on; warn (running but (unhealthy): yellow border, "non sano"); off (grey, not clickable). A stopped container keeps its card if it has a port label or was seen running since egos-home started.
  5. Static cards (STATIC): services that are not containers — Cockpit (9090, https), checked by connecting to the port.
  6. Links are built from the request's Host header (validated) + port; egos.home.url replaces the link (e.g. a public domain) and the card shows ↗ instead of the port.
  7. If the proxy does not answer, a banner says so and only the static cards remain.

The page refreshes the states every 15 s through /api/status and reloads itself when containers appear or disappear.

Security

  • The Docker socket goes only into the proxy. docker-proxy.cfg replaces the image's haproxy template and allows only GET /containers/json and GET /_ping; everything else answers 403. With the image's own CONTAINERS=1 mode, /containers/<id>/json would expose every container's environment variables (passwords) and /containers/<id>/logs its logs to anything that can reach the proxy port.
  • The proxy listens on 127.0.0.1:23750 (reachable by host processes and host-network containers), runs with cap_drop: ALL and no-new-privileges; it is not read-only because the image writes its haproxy.cfg at start.
  • egos-home: read-only container, user 1000, host network (needed for the port probes); it has no authentication — it shows only links, on the LAN.

Risks and limits

  • The stack now pulls two more images (python:3.13-alpine, tecnativa/docker-socket-proxy, both pinned by digest). As for the other images, a failed pull makes docker compose up fail and the deployment retries at the next boot.
  • Port 8000 must be free on the box.
  • Boxes installed before 4.3 do not get egos-home by themselves (no egos-update yet): the files and the two services have to be added to ~/app/repos by hand.

Storage

egos-storage
Path on the system /usr/local/sbin/egos-storage
Generated by EgOS4-amd64.sh and EgOS4-arm64.sh, section 11b (heredoc STORAGE_EOF, identical in the two scripts)
Language Bash (set -euo pipefail), with embedded Python 3 blocks
Run as root only (sudo); otherwise it exits with "Run with sudo."
Version EgOS 4.3.0

What it is for

It manages the EgOS storage pool: a mergerfs filesystem mounted on /srv/egos/pool that joins the folder /srv/egos/local (on the system disk) and the data disks /srv/egos/disks/dataN (one ext4 per disk, no RAID: if you lose a disk you lose its files, not the pool).

The pool exists from the first boot. The stack (Jellyfin, Immich, Samba) always points to /srv/egos/pool/..., so adding or removing a disk never changes a path.

Situation Pool branches Where new files go
No data disk local=RW system disk
One or more data disks data1=RW:data2=RW…:local=NC data disks (NC = "no create": local stays readable/writable but takes no new files)
A disk missing at boot only the disks present + local pool "degraded", Jellyfin held stopped until the disk is back

Note — With minfreespace=20G a branch with less than 20 GB free takes no new files. If every data disk is below that threshold (or the disk is smaller than ~20 GB) writes fail with EROFS, because local is NC. This is intended: the system disk no longer fills up.

Functions

fstab handling

Every rewrite goes through a temporary file: NUL/control bytes are dropped and the result is checked before replacing the real fstab (an interrupted write can leave NUL bytes and an unmounted disk).

fstab_commit <candidate_file>

Validates and installs a candidate fstab.

  1. sync of the temporary file.
  2. findmnt --verify --tab-file: counts only parse errors (an unplugged nofail disk is an "error" for --verify but a legitimate state here).
  3. Checks that the / line still exists.
  4. If all is well: backup copy in /etc/fstab.egos-prev, atomic mv, sync. If it fails: prints the output, deletes the candidate, returns 1 and does not touch /etc/fstab.
fstab_del <mountpoint>

Removes the (uncommented) lines whose field 2 is <mountpoint>, stripping NULs; then fstab_commit.

fstab_add <line>

Appends a complete line at the end (after stripping NULs); then fstab_commit.

Concurrency

storage_lock <seconds>

Opens /run/egos/storage.lock on descriptor 9 and takes a flock, waiting at most <seconds> (0 = fail at once). It keeps the Cockpit job, a shell command and the udev reattach from overlapping (e.g. add formats a disk labelled egos-dataN and udev "sees" a pool disk appear). Taken with 0 seconds by add, link, remove, reattach, remount, drain; with 900 seconds by _autoreattach.

MOTD warning

motd_update <missing_disks>

Writes (or deletes, if the argument is empty) a block at the top of /etc/motd delimited by *** EgOS STORAGE WARNING … *** end of EgOS storage warning ***. The block lists the missing disks and, if HELD exists, adds "Jellyfin is stopped until it is back". The rest of the file is preserved; the file is replaced only if the content changes.

The pool

Golden rule (comment in the code): never unmount or restart the pool under a running stack. The containers would keep their bind mounts on the old, dead FUSE mount and see empty folders. Every change is applied hot through the branches extended attribute.

pool_mounted

True if /srv/egos/pool is mounted (findmnt).

configured_disks

Lists the /srv/egos/disks/data* mount points present in fstab, sorted data1, data2, … (sort -V).

missing_disks

Among the configured disks, prints those that are not mounted.

branch_list

Builds the branch string for mergerfs: the mounted data disks first (=RW), local last. local is =RW if no data disk is configured, =NC otherwise.

update_state

Updates the state in /run/egos: if disks are missing it writes the list to pool-degraded and removes the pool-ok gate; otherwise it deletes pool-degraded and creates pool-ok. Finally it calls motd_update.

pool_start

systemctl start egos-pool.service and checks that the pool is mounted. The mergerfs daemon must live in the service's cgroup, not the caller's: started from the Cockpit job it would be killed when the job ends.

pool_sync

Hot branch update. If the pool is not mounted, it starts it (pool_start) and calls update_state. Otherwise it writes branch_list into the user.mergerfs.branches attribute of the control file /srv/egos/pool/.mergerfs (srcmounts is read-only in Debian 13's mergerfs), then update_state. Returns 1 if the attribute cannot be written.

mfs_branches <value>

Writes the branches attribute directly; used by do_remove with -/path to detach a single branch.

guard_dir <dir> / unguard_dir <dir>

If <dir> is not a mount point, makes it immutable (chattr +i) / unlocks it (chattr -i). An empty mount point must never receive files: mounting over it works, writing into it does not.

The egos-pool service

do_pool_run (command _pool)

ExecStart of egos-pool.service.

  1. Exits if the pool is already mounted.
  2. Migration: installs older than 4.2 mounted the pool from fstab; if it finds that line it removes it (fstab_del) and runs daemon-reload.
  3. Makes the pool mount point and those of the configured disks immutable (guard_dir).
  4. Waits up to DISK_WAIT seconds (60) for missing disks to appear (slow USB).
  5. update_state; if some disk is still missing it prints DEGRADED: ….
  6. exec mergerfs -f -o $MFS_OPTS <branches> /srv/egos/pool (in the foreground: the process is the service).
do_pool_ready (command _pool-ready)

ExecStartPost: waits up to DISK_WAIT + 30 seconds for the pool to show as mounted. This way the unit is "started" only once the pool is really there (docker and smbd start after it).

Protecting Jellyfin

Docker restarts its own containers at boot, before any EgOS unit can step in. That is why the compose file mounts the gate /run/egos/pool-ok inside Jellyfin with create_host_path: false: if the gate does not exist Docker refuses to start Jellyfin. This way the library scan never sees missing titles (it would delete them together with their metadata and watch history).

jellyfin_release

If HELD exists, runs docker start jellyfin; if that succeeds, deletes HELD.

do_guard (command _guard)

Run by egos-pool-guard.service after docker and the deployment.

  • Degraded pool: waits up to 60 s for the jellyfin container to exist, creates HELD; if Jellyfin is running (stack installed before the gate existed) it stops it with docker stop, otherwise it records that the gate keeps it off. Updates the MOTD.

  • Complete pool: jellyfin_release.

Reattach

do_reattach (commands reattach, remount)

For each missing disk it tries a plain mount (fails at once if the disk is absent, instead of waiting for the mount unit's timeout). Then pool_sync. If something is still missing it prints the disks and exits with code 3 ("Check cable and power… If the disk is gone for good: storage-remove"); otherwise jellyfin_release.

do_autoreattach (command _autoreattach)

Started by the udev rule 90-egos-reattach.rules when a partition labelled egos-data* appears.

  1. Does nothing if egos-pool.service is not active (at boot the service itself takes care of it).
  2. udevadm settle (several disks plugged in together = a single pass), then storage_lock 900.
  3. Looks, among the missing disks, for those whose fstab source (UUID=…) can now be found (findfs). It also considers the "stale" state: pool marked degraded but no disk missing any more.
  4. If there is something to do it runs do_reattach, writing the output to job.log (visible in Cockpit as "Last operation") and to the journal.

Link (legacy installs)

env_get <key>

Reads the value of <key> from the stack's .env file ($ENVF), last occurrence.

move_tree <env_key> <destination>

Moves the folder named by a .env key onto the pool, with verification:

  1. skips if the key is missing, already equal to the destination, or if the folder does not exist;
  2. checks the free space (size + 1 GiB margin);
  3. rsync -aHAX --numeric-ids;
  4. check 1: a second rsync in dry-run must have nothing to transfer;
  5. check 2: same number of files at source and destination;
  6. renames the original to <folder>.pre-pool and updates .env. On any error the source stays intact and .env does not change.
do_link (command link)

For installs older than 4.2 (the stack was not on the pool). Finds the user from /var/lib/setup-data.json, asks (or takes from --yes/--immich) whether to move the Immich originals too, saves .env (.env.bak.<date>), stops the stack (docker compose down), calls move_tree for JELLYFIN_MEDIA_LOCATION → /srv/egos/pool/media and, if requested, UPLOAD_LOCATION → /srv/egos/pool/immich/upload, fixes the permissions, updates the path of the Samba share [media], restarts smbd/wsdd2 and the stack. Immich's Postgres database always stays on the system disk (a DB on a USB disk is easily corrupted). The .pre-pool folders have to be deleted by hand.

Disk integrity test

verify_disk <mountpoint>

A fake-capacity device accepts writes, says "ok" and returns different data: mkfs succeeds, the ext4 gets corrupted later. The test:

  1. generates 128 MiB of random data in /var/tmp;
  2. writes it to the disk with conv=fdatasync, within 180 s (otherwise: disk unusable at this speed);
  3. drops the cache (drop_caches) and compares byte by byte (cmp);
  4. checks that the kernel logged no new EXT4-fs error in dmesg;
  5. prints the approximate write speed. Returns 1 at the first failure.

Removal

do_remove (command remove)

Retires a branch without formatting. Run it with the disk still connected (it also works if it is already unplugged, but then any writes not yet on the disk are lost).

  1. Lists the branches, picks the one from --branch or from numeric input.
  2. Works out whether the disk is connected (ATTACHED); warns if it is the last data disk (new files go back to the system disk).
  3. Asks to type the branch name exactly (dataN).
  4. Detaches the branch hot (mfs_branches -<path>).
  5. sync.
  6. Unmounts: with the disk connected the unmount must succeed cleanly; if something keeps the branch open it shows lsof, puts the branch back in the pool and stops ("Do NOT unplug the disk"). With the disk absent it uses umount -f/-l.
  7. Removes the line from fstab; if the empty folder remains, unlocks and removes it; if it is not empty it warns (files ended up on the system disk).
  8. pool_sync; if no disk is missing any more, jellyfin_release.
  9. Removes the device from the kernel (/sys/block/<disk>/device/delete) and prints "YOU CAN NOW SAFELY UNPLUG THE DISK".

Adding

sys_disk

The disk holding / (e.g. /dev/nvme0n1), found with findmnt + lsblk PKNAME.

candidates <system_disk>

Python over lsblk -J: lists the whole disks that can be added, as TSV (name size bus model mountpoint). Excludes the system disk, zram, loop, fd (floppy controllers on x86 boards and VMs), eMMC boot/RPMB areas.

do_disks_json (command disks --json)

Converts the output of candidates into JSON (name, size, tran, model, mountpoints). Stops if the system disk cannot be determined.

do_add (command add, default)
  1. Determines the system disk (if it cannot, it stops: it never risks formatting it).
  2. Lists the candidates; picks from --disk or from numeric input.
  3. Shows the contents; stops if there are mounted partitions.
  4. Asks to type the device name exactly.
  5. Picks the first free dataN: it never reuses the name of a configured but temporarily absent disk (its fstab line would be overwritten).
  6. wipefs -a, GPT table, one partition at 100 %, mkfs.ext4 -L egos-dataN -m 1.
  7. Creates the mount point (immutable), adds to fstab UUID=… /srv/egos/disks/dataN ext4 defaults,nofail,noatime,x-systemd.device-timeout=60 0 2, mounts.
  8. verify_disk: if it fails it unmounts, removes the fstab line, removes the folder and stops ("the disk does NOT join the pool").
  9. Gives ownership to the user created at setup (Samba and the services can write).
  10. pool_sync (hot attach, no service restart). If it fails it exits with code 2 and suggests storage-reattach.

Drain

do_drain (command drain)

Moves files from /srv/egos/local to the data disks keeping the same relative path: no service notices.

  1. Requires at least one mounted data disk and the pool mounted.
  2. Greedy plan (Python): files from largest to smallest, each onto the disk with the most space, keeping 20 GiB in reserve per disk (like minfreespace). Skips files changed in the last 10 minutes and the .immich markers. Prints the plan and the files that do not fit.
  3. For each disk: rsync -aHAX --from0 --files-from=… --remove-source-files (rsync writes to a temporary name and renames at the end: nobody ever reads a half-written file).
  4. The folder tree and the .immich markers always stay on the system disk: if every disk is removed the stack finds its folders again (Immich does not start without the markers).
  5. Reports how many files are left; exits with 1 if some move failed (run it again to retry).

Jobs

do_start_job <command…> (command job)

Accepts only add|remove|link|remount|reattach|drain. Refuses if egos-storage-job is already active, then systemd-run --unit=egos-storage-job --collect --setenv=HOME=/root … egos-storage _job <command…>.

do_run_job <command…> (command _job)

Inside the unit: writes the header == <date> egos-storage … to job.log, runs the command with stdin from /dev/null appending everything to the log, closes with == END rc=<code> <date> and returns the code.

Final dispatcher

Takes storage_lock 0 for the commands that change something, then routes CMD to the matching function; an unknown command prints the usage and exits with 1.

Principle

The page is only a front end for egos-storage: it reads the state with egos-storage status --json and disks --json and starts every change as egos-storage job … (a systemd unit). Closing the page never interrupts a format or a copy. All safety checks stay in egos-storage. Cockpit administrative access is required (superuser: "require").

           (arm64) egos-growroot ─→ first-boot-setup ─→ setup-webapp.sh ─→ reboot
           egos-pool ─→ docker, smbd ─→ egos-pool-guard

2nd boot:  egos-pool ─→ docker ─→ docker-compose-startup (after time-sync + DNS) ─→ deploy-compose.sh
                                └→ egos-pool-guard

always:    udev "egos-data*" added ─→ egos-reattach ─→ egos-storage _autoreattach

udev rule

/etc/udev/rules.d/90-egos-reattach.rules:

ACTION=="add", SUBSYSTEM=="block", ENV{DEVTYPE}=="partition", ENV{ID_FS_LABEL}=="egos-data*", \
  TAG+="systemd", ENV{SYSTEMD_WANTS}+="egos-reattach.service"

udev must not run long jobs (RUN+= is killed after a few seconds): that is why it starts a service. At boot every present disk is "added": in that case _autoreattach does nothing.

qbt-sort.py
Path extras/qbtt/scripts/qbt-sort.py → in the container /scripts/qbt-sort.py (read-only)
Generated by section 11a of the EgOS4 scripts
Started by qBittorrent, "Run external program on torrent finished": python3 /scripts/qbt-sort.py "%K"
Log /config/qbt-sort.log (on the host: qbittorrent/config/qbt-sort.log)
Trial run docker exec qbittorrent-nox python3 /scripts/qbt-sort.py <hash> --dry-run

Purpose

Sorts completed torrents into /Films, /SerieTv or /Musics/<Artist>/<Album>/ (the layout Jellyfin expects). It uses the Web API (torrents/setLocation), so qBittorrent itself moves the files and seeding continues from the new location. It never makes qBittorrent fail: every exception is logged and the script exits with 1.

LOG, CONF log file and qBittorrent.conf

DEST video_movie → /Films, video_series → /SerieTv, audio → /Musics
EXT_VIDEO, EXT_AUDIO recognised extensions
EXT_RISKY executables and scripts (exe, msi, bat, ps1, sh, jar, apk, dmg, deb, …)
WARNING_FILE POTENTIALLY HARMFUL (Italian POTENZIALMENTE DANNOSO before 4.2.3)
RE_SERIES S01E02, S01, 1x02, Season 1/Stagione 2, Complete Series, Ep 01 (season/stagione only when followed by a number: "The Four Seasons" is a film)
RE_YEAR, RE_TAG title + year (takes the last one: "Blade.Runner.2049.2017"); cut at quality tags (1080p, bluray, x265, ita, …)
RE_FEAT, RE_ARTIST_ALBUM removal of "feat./ft./featuring"; "Artist - Album" pattern

main() see below

Flow of main()

  1. Arguments: <hash> and optional --dry-run.
  2. wait_for_move; if the torrent does not exist → ERROR.
  3. Reads the files (torrents/files).
  4. Risky files → mark_risky, log HOLD, the torrent stays in /downloads.
  5. classify; no audio/video → SKIP.
  6. Works out destination and renaming: - single-file film → folder Title (Year); - film already in a folder → renames the folder to Title (Year); - audio → /Musics/<Artist>/<Album> (artist folder created if missing, album with free_name).
  7. Already in the right place → SKIP; destination not mounted → ERROR.
  8. --dry-run → log DRY and stop.
  9. torrents/renameFolder if needed, torrents/setLocation, waits for the move to finish; if the location has not changed (e.g. permissions) → ERROR, otherwise MOVE.

Log prefixes: MOVE, SKIP, HOLD, WARN, MKDIR, DRY, ERROR.

audiotags.py
Path extras/qbtt/scripts/audiotags.py (imported by qbt-sort.py)
Generated by section 11a of the EgOS4 scripts
Language Python 3, standard library only (the qBittorrent image has no mutagen)

Purpose

Minimal reader for the albumartist, artist, album tags. Formats: MP3 (ID3v2.2/2.3/2.4 + ID3v1), FLAC, Ogg Vorbis, Opus, M4A/MP4. Any other format → empty tags.

read_tags(path) -> {"albumartist": str|None, "artist": str|None, "album": str|None}

Command-line use (debugging): python3 audiotags.py file1.mp3 file2.flac prints the name and tags.

Name Contents

VORBIS_MAP ALBUMARTIST/ALBUM ARTIST → albumartist, ARTIST, ALBUM
MP4_MAP, MP4_CONTAINERS atoms aART, ©ART, ©alb; containers moov udta meta ilst

Functions

Function Description
_empty() dictionary with the three keys set to None
_clean(s) NUL → /, strips spaces and / at the edges, empty string → None
_syncsafe(b) decodes an ID3 "syncsafe" integer (7 bits per byte)
